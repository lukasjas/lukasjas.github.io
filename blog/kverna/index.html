Kverna: a document is a view of a fact graph

4 October 2026

Kverna is an application I built between March and June 2026. It produces two documents for a mobile network site: the technical site survey report (TSSR), which describes what will be built and where, and the bill of quantities (BOQ), which lists every item needed to build it.

It does that under two constraints. Every value in the output can be traced to where it came from. Anything that cannot be derived is listed as missing, with a reason, and is never filled in.

The code is at github.com/lukasjas/kverna.

The problem

I wrote these documents by hand for about a year, for a Norwegian mobile operator. The TSSR is a Word file and the BOQ is an Excel file. The same value appears in several places across both. The number of sectors on a site decides the number of radios, which decides cable counts, which decide BOQ lines. Change one and you update the rest yourself.

Word and Excel do not check that you did. The checking is done by people, after the document is written: the contractor reviews the TSSR for completeness before it goes to the operator, and the operator approves it. What a reviewer catches comes back as a revision. What a reviewer misses goes into the BOQ, and a wrong BOQ line becomes wrong material on site, a team that cannot install, and a re-order.

The model

Kverna treats the document as a view, not as the thing you edit.

Facts. A fact is a key and a value: site_configuration = NLLL, antenna_height_m = 24. Facts are append-only. A changed value is a new row that supersedes the old one, so the history of every value stays in the database. Each fact records its source: typed by the engineer, picked from a catalog, highlighted in a source PDF, or derived by a rule.

Rules. A rule is a row in a table, not a branch in the code. This is one, abridged:

{
  "pattern": "site_configuration",
  "condition": "len(site_configuration) > 1",
  "output_key": "sector_count",
  "output_expr": "len(site_configuration) - 1",
  "scope_type": "operator",
  "description": "Sector count = letters after the prefix.",
  "cites": [
    { "clause": "4.1", "title": "The site model specification" }
  ]
}

When site_configuration is written, the rule fires and writes sector_count. That new fact can trigger further rules. The engine repeats until nothing changes. The rule carries a citation to the clause of the operator's specification it implements.

Documents. A renderer reads the current facts and fills the template. It has no database access and no logic of its own.

Two rules of precedence matter to the person using it. A value the engineer entered by hand is never overwritten by a derived one. And a rule scoped to one operator beats a general rule for the same output.

The two guarantees

Trace. For any value in the output, trace_fact returns the chain: value, the rule that produced it, the facts that rule read, the source of each of those facts, and the specification clause the rule cites. Rule inputs are reconstructed from the rule's expression, not logged at write time, so the trace cannot drift from what the rule does.

One BOQ quantity, traced: value, rule, input fact, specification clause. Demo data.

Missing. Each document type has a list of facts it requires, stored as data. list_missing_facts returns the required keys that are absent, each with the reason it is required. This mirrors the completeness check the operator runs on submission. The engine reports the gap; it does not estimate a value to close it.

The body check: six facts still missing for the TSSR, each with the reason it is required.

Where the language model sits

A language model can read a source document and propose values. Those go into a separate candidate_facts table with a pointer to the place in the source they came from. A person confirms a candidate before it becomes a fact. The model never writes a value into the final document, and the document is rendered from structured data, not generated prose.

The same gate applies when the engineer captures a value by marking it in a source PDF:

A value marked in a source PDF is confirmed before it becomes a fact.

The cost is slower automation. What it buys is that "a model helped" and "nothing is guessed" can both be true.

How it is built

  • Backend: FastAPI on Python 3.12 with raw asyncpg. No ORM, because tenant isolation depends on setting a session variable on each connection, and I wanted that explicit.
  • Database: PostgreSQL 16. Every table has a tenant_id, and row-level security does the filtering. Schema changes are hand-written SQL migrations.
  • Rule expressions: simpleeval, a sandboxed evaluator. Never eval.
  • Frontend: React, TypeScript, Vite, Tailwind.
  • Tests: the backend suite runs against a real migrated PostgreSQL, each test in a transaction that rolls back.

The services that store facts and evaluate rules contain no telecom terms. Operator knowledge lives in rule files, a product catalog, and requirement lists. Each architectural decision, with the reason and the condition for revisiting it, is in DECISIONS.md.

The reference case is a rooftop site I surveyed myself: 248 facts, 44 rules, and its real BOQ as the expected output.

What is unfinished

  • One site type, one operator. The claim that the engine carries to other document types is argued in the design and not yet shown with a second domain.
  • The missing-facts check is direct only. If a missing fact could itself be derived from another missing fact, it does not walk upstream.
  • Rules do not learn. When an engineer overrides a derived value, that is recorded and nothing reads it.
  • Retrieval over the specification scored 57% on a 100-question test set when I last measured it. That is a baseline, not a result.
  • No offline mode. A rooftop does not always have signal.
  • It has been demonstrated to people in the industry. It has not been used on a live job.
