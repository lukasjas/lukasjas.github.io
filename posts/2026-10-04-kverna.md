Kverna is an application I built between March and June 2026. It produces two documents for a
mobile network site: the technical site survey report (TSSR), which describes what will be built
and where, and the bill of quantities (BOQ), which lists every item needed to build it.

Kverna treats the document as a view, not as the thing you edit. Underneath it is a graph of
facts and the rules that connect them. That gives two constraints. Every value in the output can
be traced to where it came from. Anything that cannot be derived is listed as missing, with a
reason, and is never filled in.

## The problem

I wrote these documents by hand for about a year, for a Norwegian mobile operator. The TSSR is a
Word file and the BOQ is an Excel file, and the same value appears in several places across both.
The number of sectors on a site decides the number of radios, which decides cable counts, which decide
BOQ lines. Change one and you update the rest yourself.

Word and Excel do not check that you did. The checking is done by people, after the document is
written: the contractor reviews the TSSR for completeness before it goes to the operator, and the
operator approves it. What a reviewer catches comes back as a revision. What a reviewer misses goes
into the BOQ, and a wrong BOQ line becomes wrong material on site, a team that cannot install, and
a re-order.

That is one narrow part of the picture. Why errors happen in the work before a site is built has
deeper and wider causes than an unchecked value, and this post does not cover them. It describes
the model I built, how it functions, and how it is used.

## The model

The graph has three parts: facts, rules, and the documents rendered from them.

![Diagram: sources feed facts, facts trigger rules, rules derive more facts, documents are rendered from the current facts, and required facts that are absent are listed as missing.](/images/kverna/flow.svg)

**Facts.** A fact is a key and a value: `site_configuration = NLLL`, `antenna_height_m = 24`.
Facts are append-only. A changed value is a new row that supersedes the old one, so the history
of every value stays in the database. Each fact records its source: typed by the engineer, picked
from a catalog, highlighted in a source PDF, or derived by a rule.

**Rules.** A rule is a row in a table, not a branch in the code. This is one, abridged:

```json
{
  "pattern": "site_configuration",
  "condition": "len(site_configuration) > 1",
  "output_key": "sector_count",
  "output_expr": "len(site_configuration) - 1",
  "scope_type": "operator",
  "description": "Sector count = letters after the prefix.",
  "cites": [
    { "clause": "4.1", "title": "The site model specification" }
  ]
}
```

When `site_configuration` is written, the rule fires and writes `sector_count`. That new fact can
trigger further rules, and the engine repeats until nothing changes. The rule carries a citation to
the clause of the operator's specification it implements.

**Documents.** A renderer reads the current facts and fills the template. It has no database
access and no logic of its own.

Two rules of precedence matter to the person using it. A value the engineer entered by hand is
never overwritten by a derived one. And a rule scoped to one operator beats a general rule for the
same output.

## The two guarantees

**Trace.** For any value in the output, `trace_fact` returns the chain: value, the rule that
produced it, the facts that rule read, the source of each of those facts, and the specification
clause the rule cites. Rule inputs are reconstructed from the rule's expression, not logged at
write time, so the trace cannot drift from what the rule does.

![The provenance panel for one BOQ quantity: the value 3, the rule that produced it, the input fact it read, and the specification clause the rule cites.](/images/kverna/trace.png)

*One BOQ quantity, traced: value, rule, input fact, specification clause. Demo data.*

**Missing.** Each document type has a list of facts it requires, stored as data. `list_missing_facts`
returns the required keys that are absent, each with the reason it is required. This mirrors the
completeness check the operator runs on submission.

![The body check panel listing six missing facts, each with the reason it is required.](/images/kverna/body-check.png)

## Where the language model sits

A language model can read a source document and propose values. Those go into a separate
`candidate_facts` table with a pointer to the place in the source they came from. A person confirms a
candidate before it becomes a fact. The model never writes a value into the final document, and
the document is rendered from structured data, not generated prose.

The same gate applies when the engineer captures a value by marking it in a source PDF:

![A dialog asking the engineer to confirm a value captured from a radio plan PDF before it becomes a fact.](/images/kverna/confirm-capture.png)

*A value marked in a source PDF is confirmed before it becomes a fact.*

Automation is slower this way.

## How it is built

Facts, rules and requirement lists are all tables in PostgreSQL 16. Every table has a
`tenant_id`, and row-level security keeps one company's sites out of another's queries. That
isolation depends on a session variable set on each connection, so the FastAPI backend uses raw
asyncpg with no ORM: I wanted that step visible in the code. For the same reason the tests run
against a real migrated database, each in a transaction that rolls back. Row-level security cannot
be tested against a mock.

Rule expressions are evaluated by `simpleeval`, a sandboxed evaluator. Rules are data that anyone
with access can write, so they never go through `eval`. The frontend is React and TypeScript.

The services that store facts and evaluate rules contain no telecom terms. Operator knowledge
lives in rule files, a product catalog, and requirement lists.

The reference case is a rooftop site I surveyed myself: 248 facts, 44 rules, and its real BOQ
as the expected output.

## What is unfinished

- One site type, one operator. The claim that the engine carries to other document types is
  argued in the design and not yet shown with a second domain.
- The missing-facts check is direct only. If a missing fact could itself be derived from another
  missing fact, it does not walk upstream.
- Rules do not learn. When an engineer overrides a derived value, that is recorded and nothing
  reads it.
- Retrieval over the specification scored 57% on a 100-question test set when I last measured
  it. That is a baseline, not a result.
- No offline mode. A rooftop does not always have signal.
- It has been demonstrated to people in the industry. It has not been used on a live job.
